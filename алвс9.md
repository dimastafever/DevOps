## Задание 1. Статус файла

### Что в задании

Приводится скрипт, который создаёт файл, добавляет его в индекс и затем изменяет.
Требуется определить, в каком статусе находится файл.

```
#!/bin/bash
find . ! -name '*.sh' ! -name '.' -exec rm -rf {} +
git init
echo IC > file
git add file
echo 2 >> file
git status
```

### Результат и объяснение

Файл `file` находится **в двух состояниях одновременно**:

1. **В индексе (staged)** — как новый файл с содержимым `IC` (его добавили командой `git add file`).
2. **В рабочей директории изменён (unstaged)** — отличается от индекса (к нему дописали строку `2`).

Команда `git status` покажет примерно:

```
Changes to be committed:
  new file:   file

Changes not staged for commit:
  modified:   file
```

Это ключевой момент: файл может быть одновременно и в индексе, и иметь незакоммиченные
изменения в рабочей директории.

## Задание 2. Сравнение `git add .` и `git add --all`

### Что в задании

Запускается скрипт, в котором из поддиректории `dir2` выполняется `git add .`, а затем
после `git reset` — `git add --all`. Нужно объяснить разницу.

```
#!/bin/bash
find . ! -name '*.sh' ! -name '.' -exec rm -rf {} +
rm -rf .git
mkdir -p project/dir1 project/dir2
cd project
git init
echo "original" > dir1/file1.txt
echo "original" > dir2/file2.txt
git add .
git commit -m "initial commit"
rm dir1/file1.txt
echo "updated" >> dir2/file2.txt
cd dir2
git add .
git status
git reset
git add --all
git status
```

### Объяснение

- **`git add .`** — добавляет изменения **только в текущей директории и её поддиректориях**
  (относительно места вызова команды). Выполняя `git add .` из `dir2`, мы зафиксируем
  изменение `file2.txt`, но **не увидим** удаление `dir1/file1.txt`, потому что `dir1`
  находится вне текущей директории.
- **`git add --all`** (или `git add -A`) — добавляет изменения **во всём репозитории**,
  независимо от текущей рабочей директории. Именно поэтому при `git add --all` фиксируется
  и удаление `file1.txt`, и изменение `file2.txt`.

## Задание 3. `git stash`

### Что в задании

Скрипт имитирует работу в ветке `feature/login`, затем возвращается в `main`, создаёт
файлы `login.html` и `login.js`, после чего сохраняет изменения через `git stash push -u`
и восстанавливает их командой `git stash pop`.

```
#!/bin/bash
find . ! -name '*.sh' ! -name '.' -exec rm -rf {} +
rm -rf .git
git init
echo "# Demo project" > README.md
git add README.md
git commit -m "Initial commit"
git switch -c feature/login
git switch main
echo "<form>Login</form>" > login.html
echo "console.log('Login');" > login.js
git add login.html
git status
git stash push -u -m "login feature work"
git status
git switch feature/login
git stash pop
git status
```

### Объяснение

**`git stash`** — это **временное хранилище** для незакоммиченных изменений. Оно позволяет
«отложить» текущую работу, вернуть рабочую директорию к чистому состоянию, сделать что-то
другое, а затем вернуть изменения обратно.

- **`git stash push -u -m "..."`**:
  - `-u` (или `--include-untracked`) — сохраняет **и отслеживаемые (tracked), и неотслеживаемые (untracked)** файлы.
  - `-m "..."` — ставит сообщение, чтобы было понятно, что именно сохраняется.
- **`git stash pop`** — восстанавливает сохранённые изменения и удаляет их из stash.
  Команда `git stash apply` делает то же самое, но **не удаляет** запись из stash.

Именно поэтому после `git stash push -u` файл `login.js`, который был untracked, тоже
сохранился, а после `git stash pop` в ветке `feature/login` изменения вернулись.
## Задание 4. Отмена действий в git

### Что в задании

Рассматриваются три способа отмены действий в Git: `git rm --cached`, `git commit --amend`
и `git reset` (мягкий / жёсткий). Приводится скрипт с демонстрацией каждого из них.

### Объяснение

#### 1. `git rm --cached` (удаление из индекса)

Убирает файл из индекса, но **не удаляет его физически** с диска:

```
git rm --cached file
```

Файл переходит из состояния **staged** (добавлен в индекс) в **untracked**
(не отслеживается Git). При этом сам файл остаётся в рабочей директории.

#### 2. `git commit --amend` (перезапись последнего коммита)

Изменяет самый последний коммит — его сообщение и/или содержимое:

```
git commit --amend -m "Новое сообщение"
```

При этом:
- последний коммит **заменяется новым**,
- **хэш коммита изменяется**,
- история **переписывается**.

`--amend` удобен, когда нужно исправить опечатку в сообщении последнего коммита
или добавить в него забытые изменения (через `git add` перед `--amend`).

#### 3. `git reset` (возврат к предыдущим коммитам)

Команда `git reset` перемещает указатель `HEAD` на выбранный коммит. Различают два
основных режима:

**`git reset --soft HEAD~1`:**
- перемещает указатель `HEAD` на выбранный коммит,
- **изменения остаются в индексе** и в рабочей директории,
- сам коммит отменяется, но сделанные в нём изменения не пропадают — они
  остаются в рабочей директории для дальнейшей доработки.

**`git reset --hard HEAD~1`:**
- полностью удаляет все изменения, сделанные после выбранного коммита,
- изменения в рабочей директории и в индексе **безвозвратно стираются**,
- состояние возвращается ровно к выбранному коммиту.

Это полезно, когда нужно полностью откатиться к чистому состоянию и начать работу
с конкретного коммита.

| Режим | HEAD | Индекс | Рабочая директория |
|-------|------|--------|--------------------|
| `--soft` | перемещается | сохраняется | сохраняется |
| `--hard` | перемещается | стирается | стирается |

Существует также `git reset --mixed` (по умолчанию), который перемещает `HEAD` и сбрасывает
индекс, но **не трогает** рабочую директорию.

## Задание 5. Конфликты в git

### Что в задании

Скрипт создаёт репозиторий с ветками `main` и `feature`, в обеих изменяется один и тот же
файл `file.txt`. Затем выполняется `git merge feature`, и возникает **конфликт слияния**.
Требуется проанализировать содержимое конфликтного файла.

### Объяснение

**Конфликт слияния** возникает, когда две ветки изменяют **одни и те же строки одного
файла** и Git не может автоматически решить, какую версию принять.

После `git merge feature` файл `file.txt` будет содержать маркеры конфликта:

```
<<<<<<< HEAD
строка из main ветки (другая)
=======
строка из feature
>>>>>>> feature
```

- **`<<<<<<< HEAD`** — начало секции с содержимым текущей ветки (там, где мы находимся).
- **`=======`** — разделитель между версиями.
- **`>>>>>>> feature`** — конец секции с содержимым ветки `feature`.

Чтобы разрешить конфликт, нужно:
1. Открыть файл и вручную оставить нужную строку (или объединить обе).
2. Убрать маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
3. Добавить файл в индекс (`git add file.txt`).
4. Завершить слияние (`git commit`).

## Задание 6. `git rebase` и `git merge`

### Что в задании

Скрипт создаёт ветку `feature`, изменяющую первую строку файла, и ветку `master`,
изменяющую третью строку. Сначала выполняется `git merge master`, затем (при
раскомментировании) — `git rebase master`. Требуется сравнить историю коммитов
до и после слияния.

### Объяснение

#### `git merge` — сохраняет историю, безопаснее, подходит для публичных веток

Создаётся **новый коммит слияния**, у которого **два родителя**. История сохраняет
разветвлённую структуру — видно, откуда пришли изменения.

```
*   Merge: merge feature + master
|\
| * Feature: update line 1
* | Master: update line 3
|/
* Initial commit
```

#### `git rebase` — создаёт чистую историю, опаснее, подходит для локальной работы

Ветка `feature` **перебазируется** на конец ветки `master`. Коммит `Feature: update line 1`
переприменяется поверх коммита `Master: update line 3`. В результате история становится
**линейной**, без дополнительных коммитов слияния:

```
* Feature: update line 1
* Master: update line 3
* Initial commit
```

### Основные отличия

| Критерий | `git merge` | `git rebase` |
|----------|-------------|--------------|
| История | Сохраняет разветвлённую структуру | Делает историю линейной |
| Коммит слияния | Создаётся | Не создаётся |
| Безопасность | Безопаснее | Опаснее (переписывает историю) |
| Применение | Публичные ветки | Локальная работа |

> ⚠️ `git rebase` переписывает историю коммитов, поэтому его **не следует применять
> к публичным веткам**, на которых могут работать другие люди.
