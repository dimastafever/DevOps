## Теория

### Docker и контейнеры

**Docker** — платформа для запуска приложений в контейнерах. **Контейнер** — это
изолированная среда со своим приложением и всеми его зависимостями.

Основные понятия:

- **Образ (image)** — «слепок» с файловой системой, программой и настройками. Это шаблон.
- **Контейнер (container)** — запущенный экземпляр образа.
- **Слой (layer)** — набор изменений файловой системы; образ состоит из слоёв.
- **Dockerfile** — текстовый файл с инструкциями для сборки образа.

> ⚠️ *«о нет, если удалить контейнер, то там не будет файлов»* — важная особенность:
> все изменения, сделанные внутри запущенного контейнера (в его записываемом слое),
> **теряются при удалении контейнера**. Чтобы данные сохранялись, используют
> **volumes** (тома) — специальные области для хранения данных.

### Директивы Dockerfile

Основные инструкции Dockerfile:

| Инструкция | Назначение |
|------------|------------|
| `FROM` | Базовый образ, с которого начинается сборка |
| `RUN` | Выполнение команды в процессе сборки |
| `WORKDIR` | Установка рабочей директории |
| `COPY` | Копирование файлов из контекста сборки в образ |
| `ADD` | Копирование файлов/URL в образ (расширенная версия COPY) |
| `CMD` | Команда по умолчанию при запуске контейнера (можно переопределить) |
| `ENTRYPOINT` | Команда, которая всегда выполняется при запуске контейнера |

Пример простого Dockerfile:

```dockerfile
FROM ubuntu:22.04
WORKDIR /app
RUN apt-get update && apt-get install -y gcc
COPY main.c .
RUN gcc -o main main.c
CMD ["./main"]
```

### Кэширование слоёв

Docker собирает образ по слоям и **кэширует** их. При повторной сборке Docker
переиспользует слои, которые не изменились:

- Слои `FROM`, `RUN`, `WORKDIR` **закэшировались** — они не зависят от изменений в исходном
  коде.
- Слой `COPY` **пересобрался**, потому что изменился исходный файл.

Это важно для скорости сборки: чем раньше в Dockerfile идут «стабильные» шаги
(установка зависимостей), тем реже пересобираются тяжёлые слои.

### Многоступенчатая сборка (multi-stage build)

Сравнение двух подходов:

**c-single (одноступенчатая сборка)** — всё в одном образе. Образ содержит:
- Полный компилятор `gcc`,
- Заголовочные файлы C/C++,
- Библиотеки разработки,
- Инструменты сборки.

Такой образ **большой**, потому что в него попадают средства разработки, которые не нужны
при запуске.

**c-multi (multi-stage build)** — сборка из нескольких стадий. Итоговый образ содержит:
- Только скомпилированный бинарник `main`,
- Минимальную ОС,
- Базовые системные библиотеки.

Итоговый образ **значительно меньше**, так как в него не попадают компилятор и средства
разработки.

Пример multi-stage Dockerfile:

```dockerfile
# Стадия сборки
FROM gcc:latest AS builder
WORKDIR /app
COPY main.c .
RUN gcc -o main main.c

# Финальная стадия
FROM ubuntu:22.04
WORKDIR /app
COPY --from=builder /app/main .
CMD ["./main"]
```

### ADD vs COPY

Обе инструкции копируют файлы в образ, но есть важные различия:

- **`COPY`** — предназначен **исключительно для копирования локальных файлов** из контекста
  сборки в образ. Он **не может обрабатывать URL-адреса**, потому что работает только
  с файлами, которые существуют в контексте сборки (директория, в которой запускается
  `docker build`).

- **`ADD`** — имеет **дополнительную функциональность**:
  - если источником является **URL**, Docker извлекает и загружает файл в процессе сборки;
  - если источник — локальный **архив** (`.tar`), он автоматически распаковывается.

Правило: для простого копирования локальных файлов использовать `COPY`; для извлечения
файлов по URL или распаковки архивов — `ADD`.

### CMD vs ENTRYPOINT

Обе инструкции определяют команду, выполняемую при запуске контейнера, но по-разному:

- **`CMD`** — более гибок для контейнеров **общего назначения**, где вы хотите
  **переопределить** команду по умолчанию. Аргументы и команду из `CMD` можно заменить,
  передав свою команду в `docker run ...`.

- **`ENTRYPOINT`** — лучше подходит для контейнеров, которые **всегда должны выполнять
  определённую команду** с необязательными дополнительными аргументами. Команду из
  `ENTRYPOINT` заменить нельзя (можно только добавить аргументы), поэтому она идеальна
  для «основного процесса» контейнера.

Пример:
```dockerfile
ENTRYPOINT ["/app/main"]
CMD ["--help"]
```

Здесь `main` всегда запускается, а `--help` — аргумент по умолчанию, который можно
переопределить при запуске.

### Объём контейнера и данные

- **Образ** — неизменяема основа для контейнеров.
- **Контейнер** — запущенный экземпляр; его записываемый слой исчезает при удалении.
- **Volume** — механизм хранения данных вне жизненного цикла контейнера.
